# Hardware V2.0
---
If I were to create a Version 2.0 of my light subsystem hardware, I would mainly focus on improving reliability, debugging, and ease of integration with the rest of the team system. My current design works, but there are several areas where the hardware could be improved to make the board more stable and easier to use during testing and final integration.

One improvement would be to make the UART section clearer and more robust. In Version 1, the UART communication worked, but debugging the TX and RX paths was sometimes confusing during bring-up and testing. For Version 2.0, I would label the UART input and output paths more clearly on the schematic and PCB silkscreen so it is easier to verify the signal direction during checkoff and team integration. I would also consider adding simple UART test points so that the communication lines could be probed with a multimeter or oscilloscope. This would make it much easier to debug packet transmission problems without guessing whether the issue is in software, wiring, or board layout.

Another improvement would be in the sensor input section. My subsystem uses a photoresistor together with an ADS1115 external ADC to obtain a 16-bit light reading. Functionally, this worked well, but in Version 2.0 I would improve the signal-conditioning path around the light sensor. For example, I would review the resistor values used with the photoresistor to make sure the output range better matches the expected ADC input range. This would help maximize the useful measurement range between dark and bright conditions. I would also consider adding a small RC filter if needed to reduce noise or unstable readings. This would make the sensor readings more consistent and reduce the chance of false light/no-light transitions.

I would also improve the power section of the board. In Version 1, power distribution was one of the areas that could create confusion during testing because the board includes multiple voltage domains and supporting components. In Version 2.0, I would make the power-input path easier to verify by adding more visible test points for the major rails, especially the main input voltage, the 5V rail, and the regulated 3.3V rail. This would make troubleshooting much faster if the board powers on incorrectly. I would also review component placement in the regulator and decoupling sections to keep the layout cleaner and reduce power noise.

The I2C section could also be improved. Since the ADS1115 depends on SDA and SCL being stable, I would make sure the pull-up resistors are clearly documented and sized appropriately. I would also make the address-selection configuration more obvious in the schematic and documentation, since the ADC address matters when writing software. If another sensor or I2C device is ever added later, a clearer I2C design would make the board easier to expand.

Another area for improvement is debugging indicators. In Version 1, the board already includes LEDs, but in Version 2.0 I would make the debug LED usage more intentional. For example, I would dedicate one LED to power-good indication and another to communication or sensor-status debugging. That would make it easier to quickly tell whether the board has powered correctly, whether the code is running, and whether messages are being sent or received. During class demos and checkoff, visible indicators are very helpful because they allow the teaching team to see the subsystem response immediately.

I would also improve the connector documentation and pin labeling. Since the board connects into a daisy-chain communication system, it is very important that the connectors are easy to identify and that the signal directions are obvious. In Version 2.0, I would make the connector labels clearer on both the schematic and PCB so that there is less chance of wiring mistakes. This is especially important during final team integration, where a small connector mistake can make the whole subsystem appear nonfunctional even if the actual circuit is correct.

Finally, I would make the hardware easier to maintain by improving the schematic organization. In Version 1, the design includes several functional sections such as USB, power regulation, ESP32-S3, ADC, sensor input, and connectors. For Version 2.0, I would organize these sections even more clearly and add better comments or notes to explain signal purpose. That would help both my teammates and me understand the hardware faster when reviewing the design later.

Overall, a Version 2.0 of this board would not completely change the subsystem design, because the main architecture already works. Instead, the improvements would focus on making the board more reliable, easier to debug, easier to power correctly, and easier to integrate with the rest of the team system. The biggest priorities would be better UART debugging access, better sensor signal conditioning, clearer connector labeling, and improved power verification.
